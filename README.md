# Marketing Analytics MVP

MVP-система для сквозной аналитики рекламных размещений и оценки их эффективности.

Проект позволяет связать рекламную кампанию и конкретное размещение с пользовательскими действиями, лидом и последующей покупкой. На основе этих данных система рассчитывает количество лидов, покупателей, выручку и ROMI по каждому рекламному размещению.

---

## 1. Цель проекта

Проект реализует техническую основу будущей системы маркетинговой аналитики.

Основная задача — построить цепочку:

```text
Рекламная кампания
        ↓
Рекламное размещение
        ↓
Переход пользователя
        ↓
Взаимодействие с ботом
        ↓
Лид
        ↓
Покупка
        ↓
Атрибуция
        ↓
Выручка и ROMI
```

MVP позволяет ответить на ключевой вопрос:

> Какое рекламное размещение привело пользователя к покупке и какую выручку оно принесло?

# 2. Выполненные задачи

## Задание 3 — Техническая модель системы

Спроектирована структура хранения данных для рекламных кампаний, размещений, пользовательских действий и покупок.

Система разделяет:

* рекламные кампании;
* отдельные рекламные размещения;
* рекламные материалы;
* стоимость размещения;
* время публикации;
* пользовательские касания;
* лиды;
* покупки;
* связь между рекламным касанием и покупкой.

Это позволяет не смешивать данные о рекламе и данные о продажах и в дальнейшем расширять систему без изменения основной логики.

---

## Задание 4 — События и атрибуция

Для отслеживания пользовательского пути используется последовательность маркетинговых событий:

```text
click
   ↓
bot_start
   ↓
lead
   ↓
purchase
```

Каждое маркетинговое событие содержит информацию о пользователе, размещении и времени события.

После совершения покупки система определяет маркетинговое касание, которое необходимо использовать для атрибуции.

В MVP используется принцип **Last Touch Attribution**:

> покупка относится к последнему известному маркетинговому касанию пользователя перед покупкой.

При этом одна покупка может быть атрибутирована только одному касанию.

---

## Задание 5 — Рабочий MVP

На основе спроектированной модели реализован запускаемый MVP.

MVP:

1. загружает реальные обезличенные продажи из `base.xlsx`;
2. создаёт таблицу продаж;
3. создаёт тестовые рекламные кампании;
4. создаёт рекламные размещения;
5. генерирует тестовые пользовательские события;
6. формирует цепочки `click → bot_start → lead`;
7. связывает лидов с покупками;
8. выполняет атрибуцию;
9. рассчитывает выручку;
10. рассчитывает ROMI по размещениям.

Результат можно использовать для построения аналитического дашборда.

# 3. Архитектура проекта

Проект построен как небольшой data/analytics MVP на Python и SQLite.

```text
marketing-mvp/
│
├── backend/
│   └── seed.py
│
├── data/
│   ├── base.xlsx
│   └── marketing.db
│
└── README.md
```

### `backend/seed.py`

Основной скрипт проекта.

Отвечает за:

* загрузку исходных продаж;
* создание структуры БД;
* генерацию рекламных данных;
* генерацию пользовательских событий;
* атрибуцию покупок;
* заполнение базы данных.

### `data/base.xlsx`

Исходный обезличенный слой продаж.

Файл содержит реальные данные о покупках.

Используемые поля:

| Поле             | Назначение                            |
| ---------------- | ------------------------------------- |
| `номер студента` | обезличенный идентификатор покупателя |
| `сумма`          | сумма покупки                         |
| `курс`           | приобретённый курс                    |
| `время`          | время покупки                         |

В БД эти поля преобразуются в:

| Excel            | SQLite         |
| ---------------- | -------------- |
| `номер студента` | `student_id`   |
| `сумма`          | `amount`       |

| `время`          | `purchased_at` |

### `data/marketing.db`

SQLite-база данных, создаваемая автоматически при запуске MVP.

```text
sales
├── sale_id
├── student_id
├── amount
├── course
└── purchased_at
```

### Назначение

`student_id` — обезличенный идентификатор покупателя.

`amount` — сумма покупки.

`sale_id` — уникальный идентификатор конкретной покупки.

# 5. Рекламные кампании

## `synthetic_campaigns`

Хранит информацию о рекламных кампаниях.

```text
synthetic_campaigns
├── campaign_id
├── name
├── channel
├── start_date
├── end_date
└── budget
```

Пример:

```text
CAMP_TG_ML
Промо ML курса
Telegram
2026-08-05 — 2026-09-15
100 000 ₽
```

### Зачем отдельная таблица кампаний?

Одна кампания может содержать несколько рекламных размещений.

Например:

```text
Промо ML курса
│
├── Data Science Today
└── AI & ML Community
```

Это позволяет анализировать эффективность как отдельной кампании, так и конкретного размещения.

---

# 6. Рекламные размещения

## `synthetic_placements`

Каждая запись представляет конкретное рекламное размещение.

```text
synthetic_placements
├── placement_id
├── campaign_id
├── channel
├── placement_name
├── creative_id
├── tracking_id
├── published_at
└── cost
```

### Основные поля

**`placement_id`**

Уникальный идентификатор размещения.

**`campaign_id`**

Связь с рекламной кампанией.

**`placement_name`**

Площадка или источник размещения.

Например:

```text
Data Science Today
AI & ML Community
Junior Analyst
```

**`creative_id`**

Идентификатор рекламного креатива.

Позволяет в будущем анализировать эффективность конкретных рекламных материалов.

**`tracking_id`**

Идентификатор рекламной ссылки или метки.

Именно его можно использовать в реальной системе для определения источника перехода.

**`published_at`**

Время публикации рекламы.

Это важно для проверки корректности пользовательского пути:

```text
публикация рекламы
        ↓
переход
        ↓
лид
        ↓
покупка
```

**`cost`**

Фактическая стоимость размещения.

# 7. Пользовательские маркетинговые события

## `marketing_touches`

Таблица хранит все маркетинговые касания пользователя.

```text
marketing_touches
├── touch_id
├── student_id
├── placement_id
├── event_type
└── touched_at
```

### Типы событий

В MVP используются:

```text
click
bot_start
lead
```

Например, путь пользователя может выглядеть так:

```text
student_123

10:00  click
10:01  bot_start
10:05  lead
11:30  purchase
```

Все события связаны с одним `student_id`.

Благодаря этому можно восстановить путь пользователя от рекламы до покупки.

# 8. Атрибуция покупок

## `attribution`

Таблица связывает конкретную покупку с маркетинговым касанием.

```text
attribution
├── attribution_id
├── sale_id
├── touch_id
├── attribution_model
└── attributed_amount
```

Основная связь:

```text
marketing_touches
        │
        │ touch_id
        ▼
   attribution
        │
        │ sale_id
        ▼
      sales
```

Таким образом система может ответить:

> Какое рекламное касание привело к этой покупке?

---

# 9. Модель атрибуции

В MVP используется **Last Touch Attribution**.

Логика:

1. пользователь взаимодействует с рекламой;
2. система записывает маркетинговое событие;
3. пользователь становится лидом;
4. пользователь совершает покупку;
5. система ищет последнее маркетинговое касание перед покупкой;
6. выручка покупки относится к этому касанию и его рекламному размещению.

Пример:

```text
Data Science Today
        ↓
      click
        ↓
    bot_start
        ↓
       lead
        ↓
     purchase
      7 500 ₽
```

Результат:

```text
Data Science Today
Revenue = 7 500 ₽
```

Одна покупка не должна приносить выручку нескольким размещениям.

# 10. Генерация тестовых данных

Поскольку исходный файл содержит только информацию о продажах, в MVP дополнительно генерируются синтетические маркетинговые данные.

Это необходимо, потому что в `base.xlsx` отсутствует информация о:

* рекламных кампаниях;
* размещениях;
* переходах;
* лидах;
* рекламных креативах;
* tracking ID;
* стоимости рекламы.

Поэтому эти данные создаются программно.

При этом покупки остаются основаны на исходном `base.xlsx`.

Получается комбинация:

```text
Реальные обезличенные продажи
             +
Синтетические маркетинговые события
             ↓
       Аналитический MVP
```

# 11. Расчёт показателей

## Лиды

Количество уникальных пользователей, дошедших до события `lead`.

```text
Leads = COUNT(DISTINCT student_id)
```

---

## Покупатели

Количество уникальных пользователей, совершивших атрибутированную покупку.

```text
Buyers = COUNT(DISTINCT student_id)
```

---

## Выручка

Сумма покупок, атрибутированных рекламному размещению.

```text
Revenue = SUM(attributed_amount)
```

---

## ROMI

Основная метрика эффективности рекламы:

```text
ROMI = (Revenue - Cost) / Cost × 100%
```

Например:

```text
Расходы = 15 000 ₽
Выручка = 709 867 ₽

ROMI =
(709 867 - 15 000) / 15 000 × 100%

= 4 632,4%
```

Высокий ROMI сам по себе не является ошибкой: он зависит от размера среднего чека, количества атрибутированных покупок и стоимости рекламного размещения.

| Кампания        | Размещение         |   Расход | Лиды | Покупатели |   Выручка |  ROMI |
| --------------- | ------------------ | -------: | ---: | ---------: | --------: | ----: |
| Промо ML курса  | Data Science Today | 15 000 ₽ |  122 |         95 | 709 867 ₽ | 4632% |
| Аналитика старт | Аналитика для всех | 12 000 ₽ |  127 |         94 | 643 572 ₽ | 5263% |

Таким образом, MVP позволяет сравнивать рекламные размещения не только по количеству переходов или лидов, но и по фактической выручке.

# 13. Почему используется SQLite

Для MVP выбран SQLite.

Преимущества:

* не требует отдельного сервера БД;
* запускается локально;
* не требует настройки PostgreSQL/MySQL;
* поддерживается стандартными средствами Python;
* удобно использовать для демонстрационного проекта;
* база хранится одним файлом.

Для production-системы SQLite можно заменить на PostgreSQL без изменения общей логики модели данных.

# 16. Проверки корректности

При генерации данных выполняются проверки:

* количество атрибуций соответствует количеству уникальных атрибутированных покупок;
* один `sale_id` не должен быть атрибутирован несколько раз;
* покупатель не должен появляться в атрибуции без соответствующей покупки;
* маркетинговое событие должно происходить после публикации размещения;
* покупка должна происходить после маркетингового касания;
* количество покупателей не должно превышать количество лидов для соответствующей воронки.

Это позволяет использовать MVP не только как демонстрацию, но и как основу для дальнейшего развития системы.
